# Analyst Prompt 加载机制

## 核心结论

Prompt 不是写死的。是运行时从 `.md` 文件加载的，有**三级优先级**机制。

## Prompt 文件结构

```
skillopt/prompts/                          # 通用默认
├── analyst_error.md                       # 失败分析（patch 模式）
├── analyst_success.md                     # 成功分析（patch 模式）
├── analyst_error_rewrite.md               # 失败分析（rewrite 模式）
├── analyst_success_rewrite.md
├── analyst_error_full_rewrite.md          # 失败分析（full_rewrite 模式）
└── analyst_success_full_rewrite.md

skillopt/envs/searchqa/prompts/            # searchqa 环境专用
├── analyst_error.md                       # 定制版失败分析
└── analyst_success.md                     # 定制版成功分析

skillopt/envs/alfworld/prompts/            # alfworld 环境专用
├── analyst_error.md
└── analyst_success.md
```

## 三种 prompt 变体的区别（patch / rewrite / full\_rewrite）

这三个 prompt 对应 `skill_update_mode` 的三种模式，区别在于 **Optimizer 对 skill 文档的修改粒度**：

### 对比

| <br />   | `analyst_error.md` | `analyst_error_rewrite.md` | `analyst_error_full_rewrite.md` |
| :------- | :----------------- | :------------------------- | :------------------------------ |
| **模式**   | `patch`            | `rewrite_from_suggestions` | `full_rewrite_minibatch`        |
| **修改粒度** | 外科手术式局部编辑          | 给建议，由后续步骤重写                | 整篇推倒重来                          |
| **输出字段** | `edits`            | `revise_suggestions`       | `skill_candidates`              |
| **输出内容** | 具体的增删改操作           | 抽象的修改建议                    | 完整的新 skill 文本                   |
| **比喻**   | 改几行代码              | 写 code review 意见           | 重新写整个文件                         |

### 具体差异

**`analyst_error.md`（patch 模式）** — 做局部手术

```json
"edits": [
  {"op": "append",      "content": "新增一段"},
  {"op": "insert_after", "target": "## 答题策略", "content": "..."},
  {"op": "replace",     "target": "旧文本",      "content": "新文本"},
  {"op": "delete",      "target": "要删的文本"}
]
```

Optimizer 直接说"在哪里删、在哪里加、替换什么"，后续直接应用到 skill 文档上。

**`analyst_error_rewrite.md`（rewrite 模式）** — 只提建议

```json
"revise_suggestions": [
  {
    "type": "add_rule|remove_rule|merge_rules|reorganize|compress|clarify",
    "title": "简短标题",
    "motivation": "为什么要改",
    "instruction": "重写优化器应该怎么改",
    "priority_hint": "high|medium|low"
  }
]
```

Optimizer 不直接改，而是说"你应该加一条规则、合并这两条规则、压缩冗余内容"。后续由 `rewrite_skill_from_suggestions()` 根据这些建议整体重写 skill。

**`analyst_error_full_rewrite.md`（full\_rewrite 模式）** — 直接重写全文

```json
"skill_candidates": [
  {
    "title": "简短标题",
    "change_summary": ["改了什么1", "改了什么2"],
    "new_skill": "<完整的重写后 skill 文档>"
  }
]
```

Optimizer 直接输出一份完整的新 skill 文档，跳过了编辑/建议的中间步骤。prompt 原话："Summarize the lessons from these trajectories into one complete replacement skill document."

### 三种模式的流程对比

```
patch 模式:
  Reflect(analyst_error.md) → edits → Select(裁剪) → apply_patch → Gate

rewrite_from_suggestions 模式:
  Reflect(analyst_error_rewrite.md) → suggestions → Select(裁剪) → rewrite_from_suggestions → Gate

full_rewrite_minibatch 模式:
  Reflect(analyst_error_full_rewrite.md) → 完整新skill → Select(选1个) → 直接用 → Gate
```

从左到右，Optimizer 的参与度递增，改动幅度递增，中间抽象层递减。

### 三种模式的后续Select过程对比

| 模式                         | Select 做什么         | 候选数量                  | 说明                                              |
| -------------------------- | ------------------ | --------------------- | ----------------------------------------------- |
| `patch`                    | 按学习率裁剪 edits       | N 个 edits → L 个       | `rank_and_select()` 按相关性排序，截取前 L 个              |
| `rewrite_from_suggestions` | 按学习率裁剪 suggestions | N 个 suggestions → L 个 | 同上，裁剪的是建议而非编辑操作                                 |
| `full_rewrite_minibatch`   | **跳过**             | Aggregate 已合并成 1 个    | `edit_budget=None`，不做排序裁剪，直接用 Aggregate 产出的唯一候选 |

> full\_rewrite 模式的"选择"实际上发生在 **Aggregate 阶段**——由 LLM 在层级合并时决定保留哪些内容、丢弃哪些内容，而不是像 patch 模式那样在 Select 阶段做数值排序裁剪。三个 merge prompt 均要求 "Return exactly one item in skill\_candidates"。

## prompt 输出格式

不同模式下 analyst prompt 要求 Optimizer 返回的 JSON 格式不同（见上方三种变体）。patch 模式的四种 edit 操作：

- `append` — 在 skill 文档末尾添加
- `insert_after` — 在指定标题/文本后插入
- `replace` — 替换指定文本
- `delete` — 删除指定文本

> 注意：所有 prompt 都包含 SLOW\_UPDATE 保护指令——不要修改 `<!-- SLOW_UPDATE_START -->` 和 `<!-- SLOW_UPDATE_END -->` 标记之间的内容。

## 加载链路（以失败 minibatch 为例）

```
① adapter.get_error_minibatch_prompt()
    │
    ├─ 根据 skill_update_mode 选 prompt 名：
    │   patch 模式     → "analyst_error"
    │   rewrite 模式   → "analyst_error_rewrite"
    │   full_rewrite  → "analyst_error_full_rewrite"
    │
    └─ _load_env_prompt(name)
        │
        └─ load_prompt(name, env="searchqa")
            │
            ├─ 优先：skillopt/envs/searchqa/prompts/{name}.md  ← 环境专用
            └─ 兜底：skillopt/prompts/{name}.md                 ← 通用默认
            │
            └─ 返回内容字符串，或 None

② run_minibatch_reflect(error_system=上一步结果)
    │
    └─ run_error_analyst_minibatch(system_prompt=error_system)
        │
        └─ _resolve_prompt(system_prompt, "analyst_error", mode)
            │
            ├─ system_prompt != None → 直接用环境专用 prompt
            └─ system_prompt == None → 再试通用默认 load_prompt("analyst_error")
```

为什么有两次“通用默认”的兜底？第二层是 跨模式降级 ——保证即使配了 full\_rewrite 或 rewrite 模式但缺少对应 prompt 文件，系统也不会崩，而是退回到最基础的 analyst\_error.md 继续运行。

## 三级优先级

| 优先级   | 来源          | 路径                                                                      |
| ----- | ----------- | ----------------------------------------------------------------------- |
| 1（最高） | 环境专用 + 模式对应 | `skillopt/envs/<env>/prompts/analyst_error[_rewrite][_full_rewrite].md` |
| 2     | 通用 + 模式对应   | `skillopt/prompts/analyst_error[_rewrite][_full_rewrite].md`            |
| 3（兜底） | 通用基础版       | `skillopt/prompts/analyst_error.md`                                     |

## load\_prompt 函数

[skillopt/prompts/\_\_init\_\_.py](file:///c:/Users/huawei/Desktop/SkillOpt/SkillOpt/skillopt/prompts/__init__.py) 中的核心加载函数：

```python
def load_prompt(name: str, env: str | None = None) -> str:
    # 1. 先试环境专用路径
    if env is not None:
        env_path = os.path.join(..., "envs", env, "prompts", f"{name}.md")
        content = _read_file(env_path)
        if content is not None:
            return content

    # 2. 兜底通用路径
    generic_path = os.path.join(..., f"{name}.md")
    content = _read_file(generic_path)
    if content is not None:
        return content

    raise FileNotFoundError(...)
```

- 带缓存（`_cache` 字典）
- 先查环境专用，找不到再查通用默认

## adapter 中的方法

[skillopt/envs/base.py](file:///c:/Users/huawei/Desktop/SkillOpt/SkillOpt/skillopt/envs/base.py) 中的两个方法：

### get\_error\_minibatch\_prompt()

```python
def get_error_minibatch_prompt(self) -> str | None:
    update_mode = getattr(self, "_cfg", {}).get("skill_update_mode", "patch")
    if full_rewrite mode:
        return self._load_env_prompt("analyst_error_full_rewrite")
    if rewrite mode:
        return self._load_env_prompt("analyst_error_rewrite")
    return self._load_env_prompt("analyst_error")
```

### get\_success\_minibatch\_prompt()

逻辑相同，换成 `analyst_success` 系列文件名。

## 通用 vs 环境专用 的区别

对比通用版 [analyst\_error.md](file:///c:/Users/huawei/Desktop/SkillOpt/SkillOpt/skillopt/prompts/analyst_error.md) 和 searchqa 专用版 [analyst\_error.md](file:///c:/Users/huawei/Desktop/SkillOpt/SkillOpt/skillopt/envs/searchqa/prompts/analyst_error.md)：

| 通用版                                                    | searchqa 专用版                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------- |
| "expert failure-analysis agent for **AI agent tasks**" | "expert failure-analysis agent for **question answering tasks**"          |
| 通用失败分类                                                 | 定制失败分类：`rule_missing` / `rule_wrong` / `rule_ignored` / `answer_format`   |
| 通用分析步骤                                                 | QA 专用步骤："carefully compare each predicted answer against the gold answer" |

每个环境可以根据自己的任务特点定制 prompt，不定制就自动用通用版。成功 minibatch 的逻辑完全相同，只是换成 `analyst_success` 系列文件。
