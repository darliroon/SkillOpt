SkillOpt是怎么在没有成败轨迹对比的情况下获取需要修改的点的？
好问题——确实没有“同一题的成功轨迹”做配对对照，但有 三重替代信号 ，全在喂给 analyst 的材料里（ reflect.py:152-206 ）：

## 1. 逐题的“标准答案对比”——纵向对比的替代

每条失败轨迹的头部打包了监督信息：

关键是 Hidden Reference ：analyst 拿着“agent 实际轨迹 + 判分器的 fail\_reason + 真值答案”三样东西，可以直接定位“第几步开始偏离、最终输出差在哪”——不需要同一题的成功 rollout 来对照， 真值就是那个对照组 。

## 2. 跨批次的“共性挖掘”——横向对比的替代

单条轨迹的失败可能是个体噪声，minibatch 机制让它变成统计信号。 analyst\_error.md 的指令明确要求：

同一批 M 条失败里如果 5 条都在“没先读表头就写公式”，这就是系统性缺陷而非巧合—— “重复出现的错误”本身就把信号从噪声里滤出来了 ，作用等价于对照组。

## 3. 技能文档作为“规范对照组”——行为 vs 规则的对比

analyst 同时拿到当前 skill 全文，被要求 “Only patch gaps in the skill — do not duplicate existing content”。于是隐式的第三重对比是：

```
agent 行为  vs  skill 已有规则
  ├─ 行为错误 + skill 没写 → 知识缺口（gap）→ 补规则
  └─ 行为错误 + skill 写了 → 执行失灵（lapse）→ 强化/改写措辞
```

这正是 use\_skill\_aware\_reflection 的 defect/lapse 区分的来源——不需要任何成功轨迹，拿行为和规则文本对齐就能分类。

## 4. 成功侧完全不需要“找错”

analyst\_success.md 的任务更简单：挖掘 跨多条轨迹反复出现、且 skill 尚未覆盖 的良性模式（"patterns NOT already covered"）。它做的是归纳编码，不是差异归因，所以天然不依赖失败侧。

## 5. 补充：跨步记忆

step\_buffer\_context 把本 epoch 之前各步的 failure patterns（尤其 persistent\_fail 类）注入 prompt——上一轮学了还是错的模式会被再次点名，相当于把对比窗口从“一个 minibatch”拉长到“整个 epoch”。

一句话：配对对照被三样东西替代了——真值答案（告诉它“应该是什么”）、批次共性（告诉它“什么是系统性的”）、技能文本（告诉它“规则缺了还是没被遵守”）。 这也是为什么它敢规定“不许 hardcode 任务特定值”：泛化压力来自“共性才配进 skill”这条规则，而不是来自对照实验。

那CCE-Reflect还有什么意义？

有意义——它补的正是那三重替代信号 做不到 的洞。对照 proposal 3.1 节 列的三个局限逐个看：

## 1. 真值对比只告诉你“答案是什么”，不告诉你“哪一步是关键”

上一条说的三重信号里最强的 Hidden Reference，本质是 结果层对齐 ：agent 输出 vs 标准答案。但多步 agent 任务里，通向同一答案的行为路径有很多条——

```
真值能回答:  最终输出差在哪（公式错了/格式错了）
真值不能回答: 第 3 步"先读表头"这个动作, 是无关紧要还是成败分水岭?
```

SkillOpt 的 analyst 只能靠 LLM 推理去猜哪步关键；CCE 直接拿到 同任务的成对轨迹 ，逐步对比找 divergence point（ proposal 代码 ：第一个 action 不一致的步），分叉点之后就是候选因果差异—— 行为层归因，不用猜 。

## 2. 批次共性是相关信号，没有对照组就分不清“失败特有”还是“任务通用”

这是统计上最根本的区别：

```
SkillOpt failure 侧测的是:  P(pattern | fail)
CCE 测的是:                 P(pattern | fail) − P(pattern | 
success)   ← 因果提升量
```

一条 pattern 在 5 条失败轨迹里都出现 → analyst 判它“系统性”。但也许它在本任务的 成功轨迹里也人手一份 ——那它就只是这个领域的通用做法，不是病根，补进 skill 是无效编辑。配对对照把这类 混杂因子 （success 和 failure 共有的模式）直接消掉——和流行病学的 matched case-control study 是同一个设计。

## 3. 配对 = 方差消减，和我们聊过的 σ 是同一个原理

单条轨迹失败可能是采样随机性（前面讨论过的边缘题翻转），不一定是技能缺陷。同任务配对相当于 配对实验 ：任务内容、表格、指令全部相同，两条轨迹之间唯一的差别就是行为本身——任务间方差被完全消掉，剩下的差异全是信号。这比“跨批次重复出现”这种跨任务过滤干净得多。

## 三种方式对照

| <br /> | SkillOpt 现状                | CCE-Reflect                     |
| :----- | :------------------------- | :------------------------------ |
| 归因粒度   | 结果层（输出 vs 真值）              | 行为层（逐步 divergence point）        |
| 信号类型   | 相关（共性=系统性）                 | 因果（对照差分）                        |
| 混杂控制   | 靠 prompt 规则（“不要 hardcode"） | 靠设计（共有模式自动抵消）                   |
| 编辑风格   | analyst 自由裁量               | 最小因果编辑（避免过度修改）                  |
| 额外成本   | 0                          | 每任务多采样（proposal 估 +N/2 rollout） |

## 什么时候 CCE 价值最大

- 无真值环境 ：只有二值 reward、没有人类可读 reference 时，SkillOpt 第一重信号直接失效，CCE 几乎是唯一的归因手段
- 长程任务 ：轨迹 30+ 步时，靠 LLM 通读全轨迹猜关键步很不可靠，逐步 diff 是机械操作
- 失败集异质 ：batch 里失败原因五花八门时，“共性”过滤会把真信号平均掉；配对按任务逐一归因，不受异质性影响

## 一个诚实的现状提醒

当前 rollout 每题只跑一次，successes 和 failures 来自 不同任务 ——真·同任务配对基本不存在，proposal 里的 build\_contrastive\_pairs 会退化为 同类别配对 。同类别任务内容不同，diff 里混着任务内容噪声，不是纯行为差异——所以 proposal 才标注它需要额外 rollout 预算（多次采样同任务）才能兑现完整收益，+40.40% 也是 SkillCAT 自己框架的数字，迁移性待验。

一句话：SkillOpt 的三重信号解决的是“没有对照组时怎么凑合”——真值当对照、共性当过滤、技能文本当规范；CCE 的意义是把这个“凑合”升级成真对照实验——同任务配对差分把相关性信号变成因果性信号，代价是每题多付一次 rollout。

# 为什么 SkillOpt 现在分开反思？

当前设计有两个独立的 analyst：

| Analyst             | 看到什么                     | 做什么                |
| :------------------ | :----------------------- | :----------------- |
| analyst\_error.md   | 只看失败轨迹 + 真值答案 + skill 全文 | 找"为什么错了"           |
| analyst\_success.md | 只看成功轨迹 + skill 全文        | 找"有什么好模式还没进 skill" |

## 关键区别：混合 vs 配对

### 你说的"一起反思"（混合）

把 5 条失败 + 5 条成功丢给同一个 analyst，让它一起看。

问题 ：这 5 条成功和 5 条失败来自 不同任务 。失败的任务 A 和成功的任务 B 之间差异是 双重的 ——行为不同 + 任务内容不同。你无法区分"某行为导致失败"还是"任务 A 本身就更难"。

```
失败任务 A: 没读表头就写公式 → 答错
成功任务 B: 先读表头再写公式 → 答对

但 A 和 B 是不同的表格！A 可能表头在合并单元格里，B 是普通表格。
"没读表头"是失败原因，还是 A 的表格本来就难？
混合在一起看 → 分不清
```

```
任务 A 第1次: 没读表头 → 答错（失败）
任务 A 第2次: 先读表头 → 答对（成功）

任务内容完全相同 → 任务间方差 = 0
唯一差异 = 行为 → 因果信号纯净
```
