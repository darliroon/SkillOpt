## 二、各方法详细介绍

### 2.1 MetaClaw (Xia et al., 2026b)

**技能产物**：SKILL.md
**表示形式**：L1/L2/L3 三层 markdown
**评估机制**：L3 code gate（代码级门控）

**核心思想**：

MetaClaw 提出了一种**三层渐进式技能表示**体系，将技能文档按抽象程度分为 L1（摘要层）、L2（概览层）、L3（完整详情层）。这一设计借鉴了 OpenViking 的 L0/L1/L2 分层按需加载思路，但将其应用于技能文档本身。

**技术路线**：

1. **L1 摘要层**：技能的一句话描述 + 关键标签，用于快速检索与路由匹配（约 100 token）
2. **L2 概览层**：技能的核心步骤概要与输入输出规范，用于决定是否加载完整技能（约 2,000 token）
3. **L3 详情层**：完整的可执行策略、规则、示例与边界条件处理（无 token 限制）

Agent 在运行时先通过 L1 快速匹配，命中后加载 L2 做决策，仅在需要深度执行时加载 L3 全文，从而**显著降低 Token 消耗**。

**评估机制**：L3 code gate —— 技能的 L3 层包含可执行代码片段，评估时直接运行这些代码验证其正确性，而非依赖 LLM-as-judge。这是一种**确定性验证**，信号无歧义。

**特色**：
- 三层表示实现了"检索 → 决策 → 执行"的渐进式加载
- 代码级门控确保技能验证的可信度
- 适用于技能库规模大、需精确路由的场景

---

### 2.2 Memento (Zhou et al., 2026a)

**技能产物**：SKILL.md + case
**表示形式**：markdown + trace
**评估机制**：L3 code gate

**核心思想**：

Memento 在标准 SKILL.md 的基础上**显式附加上下文案例（case）**，将技能文档与执行轨迹（trace）绑定存储。每个技能不仅包含策略文本，还保留了产生该策略的**历史执行轨迹**，形成"策略 + 案例证据"的双轨表示。

**技术路线**：

1. **轨迹采集**：Agent 执行任务时记录完整的推理链与工具调用序列
2. **案例提取**：从成功轨迹中提取关键决策节点，形成精简 case
3. **技能绑定**：将 case 与 SKILL.md 策略文本绑定，trace 作为策略的"证据链"
4. **检索增强**：运行时不仅检索策略文本，还同时检索相关 case 作为 few-shot 示例

**评估机制**：与 MetaClaw 相同的 L3 code gate，但验证对象是"策略 + case"的组合体——即检查绑定案例后的技能在代码执行层面的正确性。

**特色**：
- 轨迹溯源使技能的学习有据可查，避免"凭空生成"
- Case 绑定为 Agent 提供了具体的执行参考
- 适用于需要可审计性、策略可追溯的场景

---

### 2.3 Trace2Skill (Ni et al., 2026)

**技能产物**：SKILL.md
**表示形式**：L2 markdown
**评估机制**：rubric judge（评分量表评判）

**核心思想**：

Trace2Skill 专注于**从执行轨迹自动提炼技能**。与 Memento 不同，Trace2Skill 不是将轨迹与技能绑定存储，而是将轨迹作为**输入**，通过分析轨迹中的成功/失败模式，自动归纳出结构化的 SKILL.md 技能文档。

**技术路线**：

1. **轨迹收集**：收集 Agent 在目标任务上的大量执行轨迹（含成功与失败）
2. **模式挖掘**：从轨迹中识别反复出现的成功策略和失败陷阱
3. **技能合成**：将识别出的模式转化为 L2 层级的 markdown 技能文档
4. **质量评分**：使用评分量表（rubric）由 LLM-as-judge 对合成技能的质量进行评估

**表示形式**：采用 L2 概览层级的 markdown，即包含核心步骤、输入输出规范和关键规则，但不展开到 L3 的完整代码级细节。这使得技能文档保持**中等粒度**，兼顾信息量与 Token 效率。

**评估机制**：rubric judge —— 使用预定义的评分量表（如正确性、完整性、清晰度、可操作性等维度），由 LLM 对技能文档进行多维度评分。相比代码门控，rubric 适用于无法直接执行验证的抽象技能。

**特色**：
- 完全自动化的轨迹 → 技能转换流程
- L2 粒度平衡了信息密度与 Token 开销
- Rubric 评估适用于非代码类抽象技能

### 2.4 AutoRefine (Qiu et al., 2026)

**技能产物**：SKILL.md dual-form（双形式技能）
**表示形式**：markdown
**评估机制**：rubric judge

**核心思想**：

AutoRefine 提出了**双形式技能**的概念——同一技能同时维护"人类可读的策略描述"和"机器可解析的结构化规范"两种表示。在迭代精炼过程中，两种形式相互校验、协同进化。

**技术路线**：

1. **双形式初始化**：从种子技能出发，同时生成自然语言策略版和结构化规范版
2. **执行评测**：Agent 使用双形式技能执行任务，收集结果
3. **差异分析**：对比两种形式在执行中的表现差异，定位不一致点
4. **协同精炼**：根据差异分析结果，同时更新两种形式，保持一致性
5. **Rubric 评估**：对精炼后的双形式技能进行评分量表评估

**评估机制**：rubric judge —— 与 Trace2Skill 类似的评分量表评估，但评估对象是双形式技能的一致性和各自质量。

**特色**：
- 双形式设计增强了技能的可读性与可执行性
- 两种形式的相互校验提供了额外的质量保障
- 适用于需要同时服务人类理解和机器执行的复杂技能

### 2.5 SkillFlow-Bench (Zhang et al., 2026j)

**技能产物**：SKILL.md patch（技能补丁）
**表示形式**：files + JSON patch
**评估机制**：benchmark verifier（基准验证器）

**核心思想**：

SkillFlow-Bench 将技能优化建模为**文件补丁操作**——不直接输出完整技能文档，而是产出对现有技能文件的增量修改（JSON patch）。这种设计使技能的版本管理、差异追踪和回滚操作变得自然且精确。

**技术路线**：

1. **基准任务集**：构建覆盖多场景的标准化技能任务基准
2. **补丁生成**：优化器分析执行结果，产出 JSON 格式的文件补丁（add/replace/delete 操作）
3. **补丁应用**：将 JSON patch 应用到技能文件树，生成新版本
4. **基准验证**：benchmark verifier 在标准任务集上执行新版本技能，自动验证正确性
5. **通过/回滚**：验证通过则接受补丁，否则回滚

**表示形式**：files + JSON patch —— 技能以文件树形式组织（可能包含多个文件，如主技能 + 子技能 + 配置），优化产物是标准 JSON Patch 格式的增量修改。

**评估机制**：benchmark verifier —— 专用的自动化验证器，在预定义的基准任务集上执行技能并自动判断结果正确性。这是一种**强监督信号**，无需 LLM-as-judge。

**特色**：
- 补丁形式使技能演进可追溯、可回滚
- 文件树组织支持复杂技能的模块化管理
- 基准验证器提供无歧义的正确性判定
- 非常适合构建标准化的技能评估平台

### 2.6 SkillOpt (Yang et al., 2026b)

**技能产物**：SKILL.md / text skill
**表示形式**：optimized document（优化文档）
**评估机制**：held-out utility（留出集效用）

> 本综述所在项目的核心方法。

**核心思想**：

SkillOpt 提出了**"技能即权重"**的核心洞察——将 Markdown 技能文档视为神经网络的"可训练参数"，完整照搬深度学习的训练纪律（epoch / minibatch / 学习率 / 调度器 / 动量 / 验证门控），在不碰模型权重的前提下实现技能的系统性优化。

**技术路线（六阶段闭环）**：

1. **Rollout（前向传播）**：目标模型用当前技能文档执行任务，产出执行轨迹 + 分数
2. **Reflect（反向传播）**：优化器模型分析 minibatch 轨迹，识别共性失败/成功模式，产出结构化编辑补丁（add/del/replace）
3. **Aggregate（梯度聚合）**：语义相似补丁层级化合并去冗余；失败补丁优先于成功补丁
4. **Select（梯度裁剪）**：按影响/互补/通用性排序，学习率 LR 限制每步最多应用 L 条编辑
5. **Update（SGD step）**：选中编辑按操作类型应用到技能文档，产出新版本
6. **Gate（验证早停）**：新技能在留出验证集上评估，严格优于当前才接受；否则回滚，补丁进缓冲区

**Epoch 边界机制**：
- **慢更新（=动量）**：纵向对比两版技能在同一批任务上的表现，防跨 Epoch 灾难性遗忘
- **元技能（=元学习）**：累积"哪些编辑倾向有效/有害"的优化器策略记忆

**评估机制**：held-out utility —— 使用 train/val/test 三切分，在留出验证集上做严格单调门控（打平即拒、坏编辑回滚）。统计显著性由千级样本保障（如 SearchQA 1400 / SpreadsheetBench 280）。

**实验成绩**：
- 6 benchmark × 7 模型 × 3 harness = 52 格全部 best/tied-best
- GPT-5.5 直聊 +23.5 分、Codex +24.8、Claude Code +19.1
- 产物仅 300–2000 token，零额外推理调用

**特色**：
- DL 训练纪律的完整迁移，可网格搜超参、可消融实验
- 留出集门控确保泛化性，防过拟合
- 从空白技能冷启动，跨模型/跨 Harness/跨相邻任务迁移
- 部署即一份 best_skill.md，零额外调用开销

### 2.7 SkillGrad (Wang et al., 2026b)

**技能产物**：SKILL.md
**表示形式**：structured package（结构化包）
**评估机制**：loss/validation（损失/验证）

**核心思想**：

SkillGrad 与 SkillOpt 共享"技能即权重"的核心洞察，但在**梯度估计方式**上采用了不同路径。SkillGrad 将技能优化形式化为一个**可微优化问题**，通过设计可微损失函数，使技能文档的修改方向可以像神经网络梯度一样被精确计算和聚合。

**技术路线**：

1. **结构化打包**：将 SKILL.md 技能拆解为结构化包（模块化组件 + 接口规范）
2. **可微损失**：设计针对技能各组件的可微损失函数，将任务执行结果映射为连续信号
3. **梯度计算**：基于损失函数计算技能各组件的"梯度"（修改方向与幅度）
4. **梯度聚合**：聚合多任务梯度，处理冲突方向
5. **参数更新**：按梯度方向更新技能组件，验证集守门

**表示形式**：structured package —— 技能不是单一文档，而是结构化的组件包，每个组件可独立优化、替换和组合。

**评估机制**：loss/validation —— 使用显式损失函数在训练集上计算损失，在验证集上评估泛化性能。损失函数的存在使得优化过程**可量化、可调参**。

**与 SkillOpt 的区别**：
- SkillOpt 用"文本梯度"（编辑补丁）模拟梯度下降，是离散优化
- SkillGrad 设计可微损失，试图实现更接近连续优化的范式
- 两者各有优势：SkillGrad 的梯度更精确，SkillOpt 的编辑更可解释

**特色**：
- 可微损失为技能优化提供了精确的方向信号
- 结构化包支持组件级精细优化
- 适用于需要精确优化方向、可量化损失的场景

### 2.8 MUSE-Autoskill (Lin et al., 2026)

**技能产物**：SKILL.md + memory
**表示形式**：skill + per-skill memory（技能 + 逐技能记忆）
**评估机制**：unit tests（单元测试）

**核心思想**：

MUSE-Autoskill 在技能文档之外引入了**逐技能记忆（per-skill memory）**机制。每个技能不仅维护其策略文档，还维护一个独立的记忆模块，记录该技能的历史执行经验、错误模式和修复策略。这种设计使技能具备了**持续积累、逐步精化**的能力。

**技术路线**：

1. **自动技能生成**：从任务描述自动生成初始 SKILL.md
2. **执行记忆**：每次执行后，将关键经验（成功策略、失败陷阱、修复方案）写入 per-skill memory
3. **记忆检索**：下次执行同类任务时，先检索 per-skill memory 中的相关经验
4. **技能 + 记忆协同**：技能文档提供通用策略，记忆提供任务特定的经验修正
5. **单元测试验证**：为每个技能编写/生成单元测试，执行测试验证技能正确性

**评估机制**：unit tests —— 为每个技能自动生成单元测试用例，通过测试通过率评估技能质量。这是一种**确定性、可自动化**的验证方式，信号清晰无歧义。

**特色**：
- 逐技能记忆使技能具备"越用越好"的持续进化能力
- 记忆与策略分离，避免策略文档无限膨胀
- 单元测试提供可自动化、可回归的验证
- 适用于长期运行、需要持续积累经验的 Agent 系统

### 2.9 ContractSkill (Lu et al., 2026b)

**技能产物**：contract skill（契约技能）
**表示形式**：pre/postcondition artifact（前后置条件制品）
**评估机制**：deterministic checks（确定性检查）

**核心思想**：

ContractSkill 从**软件工程中的"设计契约"（Design by Contract）**思想出发，将技能建模为前置条件（precondition）、后置条件（postcondition）和不变量（invariant）的集合。技能不再是自然语言策略文本，而是一组**形式化的、可验证的约束规范**。

**技术路线**：

1. **契约定义**：为每个技能定义前置条件（执行前必须满足的状态）、后置条件（执行后必须达到的状态）和不变量（执行过程中必须保持的性质）
2. **契约执行**：Agent 在执行技能前检查前置条件，执行后验证后置条件
3. **契约违反处理**：条件不满足时触发异常处理或技能回退
4. **契约精炼**：根据执行结果精炼契约，收紧或放宽条件

**表示形式**：pre/postcondition artifact —— 技能的核心表示是形式化的前后置条件制品，而非自然语言策略文本。这使得技能的**行为规范可以被机器精确解析和验证**。

**评估机制**：deterministic checks —— 通过确定性的条件检查（而非概率性的 LLM 判断）验证技能正确性。前置条件是否满足、后置条件是否达成，都是**二值判定**，无歧义。

**与其他方法的区别**：
- 不依赖 LLM-as-judge，评估完全确定性
- 技能表示是形式化契约而非自然语言，可机器解析
- 轨迹溯源为 ✓（执行溯源）而非 ✓b（基准溯源），因为契约验证基于执行状态而非基准数据

**特色**：
- 形式化契约提供最严格的正确性保障
- 确定性检查无需 LLM 参与，评估成本极低
- 适用于安全关键场景、需要形式化保证的任务

---

### 2.10 ABSTRAL (Song et al., 2026a)

**技能产物**：SKILL.md / design doc
**表示形式**：structured markdown
**评估机制**：trace evidence（轨迹证据）

**核心思想**：

ABSTRAL 采用**自顶向下的设计驱动方法**——先从抽象的设计文档（design doc）出发，逐步精化为可执行的 SKILL.md。它强调技能的**架构设计质量**先于执行细节，通过结构化的设计文档确保技能的完整性、一致性和可维护性。

**技术路线**：

1. **设计文档生成**：从任务需求出发，生成结构化的设计文档，包含技能架构、模块划分、接口定义
2. **渐进精化**：将设计文档逐步精化为可执行的 SKILL.md，每一层精化都保持与上层设计的一致性
3. **执行验证**：Agent 使用精化后的技能执行任务，收集执行轨迹
4. **轨迹证据评估**：分析执行轨迹中的证据（成功路径、失败点、决策合理性）评估技能质量
5. **设计回溯**：当执行轨迹揭示设计缺陷时，回溯修改设计文档并重新精化

**表示形式**：structured markdown —— 技能文档采用结构化的 markdown 格式，包含层次化的设计说明和执行规范。设计文档与 SKILL.md 的关系类似"架构设计文档"与"实现代码"。

**评估机制**：trace evidence —— 不使用评分量表或代码门控，而是通过分析执行轨迹中的**证据**（如：技能是否按设计执行？关键决策点是否合理？失败是否可归因到设计缺陷？）来评估技能质量。这是一种**基于证据的定性评估**。

**与其他方法的区别**：
- 不依赖基准数据（轨迹溯源为 –），而是基于设计本身的内在逻辑
- 评估不是打分或代码执行，而是轨迹证据的定性分析
- 强调设计先行，适用于复杂技能的系统性构建

**特色**：
- 设计驱动的自顶向下方法，确保技能架构质量
- 轨迹证据评估保留了执行过程的丰富语义
- 适用于复杂技能的从零构建、需要深度设计思考的场景

## 三、Eval/Trace 信号驱动的分类框架

所有 10 种方法共享同一骨架：**执行/评估 → 信号提取 → 技能改写 → 验证接受**，差异在于"信号怎么来"和"信号怎么变成技能修改"。按此核心差异可归为三大类。

### 3.1 类别一：Eval 分数驱动 — 评估分数 → 技能修改 → 验证门控

核心逻辑：用评估分数当"损失"，产出文本编辑（类比梯度），留出集/验证器守门。

| 方法 | 信号转化方式 | 验证机制 | 关键特色 |
|---|---|---|---|
| **SkillOpt** | 评估分数 → Reflect → add/del/replace 编辑补丁（=文本梯度） | 留出集严格单调门控 | DL 同构：epoch/LR/调度器/动量/元学习全套训练纪律 |
| **SkillGrad** | 可微损失 → 连续梯度方向 → 组件级更新 | loss/validation | 结构化包，组件可独立优化，梯度更精确 |
| **AutoRefine** | rubric 评分 → 双形式差异分析 → 协同精炼 | rubric judge | 自然语言 + 结构化规范双形式相互校验 |

**共性**：信号来源是**评估分数**（held-out utility / loss / rubric），优化对象是**技能文档本身**，通过迭代改写 + 门控接受实现进化。

**差异**：SkillOpt 是离散编辑（可解释），SkillGrad 试图连续化（更精确），AutoRefine 用双形式结构增加校验维度。

### 3.2 类别二：Trace 轨迹驱动 — 执行轨迹 → 模式挖掘 → 技能合成/精化

核心逻辑：从 Agent 执行轨迹中挖掘成功/失败模式，归纳或精化出技能。

| 方法 | 轨迹利用方式 | 评估机制 | 关键特色 |
|---|---|---|---|
| **Trace2Skill** | 轨迹 → 模式挖掘 → L2 技能合成 | rubric judge | 全自动轨迹→技能转换，L2 中等粒度 |
| **Memento** | 轨迹 → case 提取 → 技能+案例绑定 | L3 code gate | 策略+证据双轨存储，可审计 |
| **ABSTRAL** | 轨迹证据 → 设计回溯 → 精化 | trace evidence | 自顶向下设计驱动，轨迹揭示设计缺陷时回溯 |

**共性**：信号来源是**执行轨迹**（完整的推理链 + 工具调用序列），优化方式是**模式归纳**而非梯度下降。

**差异**：Trace2Skill 是纯归纳（轨迹→新技能），Memento 是绑定（轨迹→案例附加到技能），ABSTRAL 是回溯（轨迹→反哺设计文档）。

### 3.3 类别三：执行验证驱动 — 确定性执行 → 条件检查 → 通过/拒绝

核心逻辑：用代码执行/单元测试/前后置条件等**确定性手段**验证技能正确性，信号无歧义。

| 方法 | 验证手段 | 技能表示 | 关键特色 |
|---|---|---|---|
| **MetaClaw** | L3 code gate（代码执行） | L1/L2/L3 三层 markdown | 三层渐进加载 + 代码级验证 |
| **MUSE-Autoskill** | unit tests（单元测试） | 技能 + per-skill memory | 逐技能记忆持续积累 + 测试回归 |
| **ContractSkill** | deterministic checks（前后置条件） | pre/postcondition 契约 | 形式化契约，二值判定，无需 LLM |
| **SkillFlow-Bench** | benchmark verifier（基准自动验证） | files + JSON patch | 补丁级版本管理 + 标准化验证平台 |

**共性**：验证信号是**确定性的**（代码跑通/测试通过/条件满足），不依赖 LLM-as-judge，无噪声。

**差异**：MetaClaw 验证代码片段，MUSE 验证测试用例，ContractSkill 验证形式化条件，SkillFlow-Bench 验证基准任务集。

### 3.4 三类对比总览

| 维度 | 类别一：Eval分数驱动 | 类别二：Trace轨迹驱动 | 类别三：执行验证驱动 |
|---|---|---|---|
| **信号来源** | 评估分数（held-out/loss/rubric） | 执行轨迹（推理链+工具调用） | 确定性执行结果（代码/测试/契约） |
| **信号强度** | 强→中（留出集强，rubric有噪声） | 中（需从轨迹归纳，含语义解读） | 强（二值判定，无歧义） |
| **优化机制** | 文本梯度/编辑补丁/双形式精炼 | 模式归纳/案例绑定/设计回溯 | 条件检查通过/拒绝 |
| **类比** | 梯度下降训练 | 数据挖掘/归纳学习 | 单元测试/形式化验证 |
| **冷启动能力** | 可从空白技能训起 | 依赖已有轨迹数据 | 需定义验证标准 |
| **代表方法** | SkillOpt, SkillGrad, AutoRefine | Trace2Skill, Memento, ABSTRAL | MetaClaw, MUSE, ContractSkill, SkillFlow-Bench |

### 3.5 正交关系说明

三类并非互斥，可正交组合：

- **SkillOpt**（类别一）的 Gate 环节可以替换为**代码门控**（类别三的 MetaClaw 方式）
- **Memento**（类别二）的 case 绑定可以加上**单元测试验证**（类别三的 MUSE 方式）
- **SkillFlow-Bench**（类别三）的 JSON patch 可以用**文本梯度**（类别一的 SkillOpt 方式）来生成

实际工程中，一个完整的技能自进化系统通常**混合使用三类机制**：用 Eval 分数驱动主优化循环（类别一），用 Trace 轨迹做辅助归纳（类别二），用执行验证做最终门控（类别三）。

## 四、方法分类与对比分析

### 4.1 按技能产物形态分类

| 形态 | 方法 | 特点 |
|---|---|---|
| **单文档型** | MetaClaw, Trace2Skill, SkillOpt, SkillGrad | 技能 = 一份 Markdown 文档，部署简单 |
| **文档 + 附加** | Memento (case), MUSE-Autoskill (memory) | 技能 + 辅助信息（案例/记忆），信息更丰富 |
| **补丁型** | SkillFlow-Bench | 技能 = 文件 + JSON patch，版本管理精确 |
| **双形式型** | AutoRefine | 自然语言 + 结构化规范，双重保障 |
| **契约型** | ContractSkill | 前后置条件制品，形式化验证 |
| **设计驱动型** | ABSTRAL | 设计文档 → SKILL.md，自顶向下 |

### 4.2 按评估机制分类

| 评估机制 | 方法 | 信号强度 | 歧义性 |
|---|---|---|---|
| **代码门控** (L3 code gate) | MetaClaw, Memento | 强 | 无歧义（代码执行结果） |
| **基准验证器** (benchmark verifier) | SkillFlow-Bench | 强 | 无歧义（自动化验证） |
| **留出集效用** (held-out utility) | SkillOpt | 强 | 无歧义（精确匹配/评分） |
| **损失/验证** (loss/validation) | SkillGrad | 强 | 可量化（连续损失值） |
| **单元测试** (unit tests) | MUSE-Autoskill | 强 | 无歧义（测试通过/失败） |
| **确定性检查** (deterministic checks) | ContractSkill | 强 | 无歧义（二值判定） |
| **评分量表** (rubric judge) | Trace2Skill, AutoRefine | 中 | 有噪声（LLM-as-judge） |
| **轨迹证据** (trace evidence) | ABSTRAL | 中 | 定性分析（需人工/LLM解读） |

### 4.3 按优化范式分类

| 范式 | 方法 | 类比 |
|---|---|---|
| **深度学习同构** | SkillOpt, SkillGrad | 技能 = 权重，编辑补丁 = 梯度，门控 = 验证早停 |
| **轨迹挖掘** | Trace2Skill, Memento | 从执行轨迹中归纳技能 |
| **增量补丁** | SkillFlow-Bench, AutoRefine | 技能 = 文件 + 补丁，版本管理 |
| **形式化契约** | ContractSkill | 技能 = 设计契约，确定性验证 |
| **设计驱动** | ABSTRAL | 自顶向下精化，设计 → 实现 |
| **记忆增强** | MUSE-Autoskill | 技能 + 记忆，持续积累 |
| **分层表示** | MetaClaw | L1/L2/L3 渐进加载 |

### 3.4 核心差异维度

| 对比维度 | 区别要点 |
|---|---|
| **优化对象** | 单文档 (SkillOpt) vs 结构化包 (SkillGrad) vs 补丁 (SkillFlow-Bench) vs 契约 (ContractSkill) |
| **梯度信号** | 文本编辑 (SkillOpt) vs 可微损失 (SkillGrad) vs 轨迹模式 (Trace2Skill) vs 条件检查 (ContractSkill) |

## 五、与 SkillOpt 的关系定位

SkillOpt（本项目核心方法）在上述方法中的定位：

| 维度 | SkillOpt 的选择 | 对比优势 |
|---|---|---|
| **技能产物** | 单份 SKILL.md | 部署最简单，零额外调用 |
| **优化范式** | 深度学习同构 | 训练纪律可复现，超参可网格搜 |
| **梯度信号** | 文本编辑补丁 | 离散编辑可解释，有界防过冲 |
| **验证机制** | 留出集严格门控 | 统计显著，泛化性有保障 |
| **记忆机制** | 慢更新 + 元技能 | 防 Epoch 间遗忘，累积优化器策略 |
| **冷启动** | 空白技能从零训练 | 无需先验知识 |
| **迁移性** | 跨模型/跨 Harness/跨任务 | 一次训练，多处复用 |

**关键差异**：SkillOpt 的轨迹溯源标记为"–"，因为它不依赖外部执行轨迹或基准数据进行技能归纳，而是通过**自建训练循环**（Rollout → Reflect → Update → Gate）从零生成训练信号。这使得 SkillOpt 不需要预先收集轨迹数据，但也意味着它无法利用已有轨迹中的丰富执行经验。而 Trace2Skill、Memento 等 ✓b 方法可以直接从已有执行轨迹中挖掘技能，冷启动更快但受限于轨迹质量。

## 六、总结

这 10 种方法代表了 2026 年 Agent 技能学习领域的全景路线图：

1. **产物形态多样化**：从单文档到双形式、补丁、契约、设计文档，各有适用场景
2. **评估机制谱系化**：从确定性代码门控到概率性评分量表，信号强度与适用范围成权衡
3. **优化范式多元化**：DL 同构、轨迹挖掘、增量补丁、形式化契约、设计驱动、记忆增强等范式互为补充
4. **共性骨架**：大多数方法共享"执行采样 → 从失败中提炼 → 改写技能 → 验证接受"的基本骨架
5. **均不更新模型权重**：所有方法的共同前提是不碰模型参数，只优化技能文档/制品

**实践建议**：
- 需要**可复现、可调参、可迁移**的基线技能 → SkillOpt
- 已有大量**执行轨迹**需转化为技能 → Trace2Skill
- 需要**形式化安全保证** → ContractSkill
- 需要**复杂技能的系统性设计** → ABSTRAL
- 需要**长期持续积累**的 Agent 系统 → MUSE-Autoskill
- 需要**精确梯度方向** → SkillGrad
- 需要**补丁级版本管理** → SkillFlow-Bench
- 需要**分层渐进加载** → MetaClaw
- 需要**案例可审计** → Memento
- 需要**人机双形式** → AutoRefine
