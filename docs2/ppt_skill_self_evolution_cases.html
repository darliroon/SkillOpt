SCENARIO 01
用户交互驱动自演进
目标：Skill 时延持续降低
演进机制 线上交互轨迹持续沉淀 → 高频问答被自动挖掘并固化为验证缓存（命中即返回，绕开 LLM/RAG）→ 用户用得越多、缓存越全、时延越低
Minerva CQ · 客服实时辅助产品
已部署于语音客服生产的 Agent Assist（arXiv 2509.12589）。从历史通话轨迹+实时使用中挖掘高频 FAQ， 新问题经启发式+本体校验后入缓存，命中即<0.5s 直答，完全绕过 RAG 链路。

SCENARIO 02
Eval 驱动自演进
目标：Skill 成功率提升
演进机制 离线评测集批量执行 → 富反馈归因诊断 → 自动生成补丁候选 → 帕累托前沿择优 → 门控上线；生产反馈回流触发下一轮重训
Databricks Agent Bricks · 信息抽取(IE) Agent
产品问题：企业级PDF/扫描件→结构化记录抽取（百页文档、70+字段嵌套Schema），前沿闭源模型太贵、开源模型精度不够。 方案：以 gpt-oss-120b 为学生模型、Claude Sonnet 4 为优化器，在 IE Bench 上跑 GEPA 反思进化 → 优化后反超此前榜首 Claude Opus 4.1 基线 +2.2 分，同时服务成本仅其 1/90。

Dropbox Dash · 搜索相关性 Judge
产品问题：Judge 原用 OpenAI o3 太贵无法全量打分，Prompt 换模型即失效。方案：GEPA 用"人机评分分歧+人类解释"作富反馈迭代适配 gpt-oss-120b → NMSE 降 45%（8.83→4.86），同成本标注量扩 10-100 倍；换模型适配从 1-2 周 → 1-2 天。
为什么越用越好 Dropbox 对生产 o3 Judge 采用"指令库增量演进"：线上分歧案例→人类写短解释→蒸馏为单行规则→DSPy 只做规则选择组装（类似"带测试的小PR"）， Judge 随分歧案例积累持续逼近人类判断，稳定不回退。
来源：Databricks AI Research 博客 (2025.09) · Dropbox 工程博客 (2026.03) · GEPA (ICLR 2026 Oral)
SCENARIO 03
高频 Skill：纯文本 md → Scripts
目标：降低模型开销与加载时延、提升执行性能
演进机制 高频稳定流程脚本化固化（scripts/ 目录）→ 脚本不进入上下文窗口、仅输出消耗 Token → 确定性执行无 LLM 推理偏差，验证后替代"每次 LLM 现推理"
Anthropic Skills 标准 + Rakuten + CData
Skills 标准采用渐进式披露：元数据常驻~50 Tokens，触发才加载指令、按需读资源；CData 实测 Skills+MCP 组合显著降低 Token 用量； Rakuten 将财务工作流脚本化为 Skills：8 小时任务 → 1 小时。
